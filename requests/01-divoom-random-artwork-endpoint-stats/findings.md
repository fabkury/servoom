# Findings

## There is no "random artwork" endpoint

Nothing in the Divoom app API draws artworks at random. Checked on 2026-09-28:

* No endpoint named for it: 22 guessed paths (`Cloud/GetRandomGallery`, `GetRandomFile`,
  `Discover/GetRandom`, ...) answer `ReturnCode 10 "Command is not match"`, with or
  without a token. The REvoom and Grayda endpoint catalogues list nothing of the kind.
* No random sort order: `FileSort` 0..7 and `RefreshIndex` 0..3 on `GetCategoryFileListV2`
  (Default and Recommend), `FileSort` on `GetSomeoneListV2`, and the tag, search, expert
  gallery, album, hot-file, theme, banner and advert endpoints all return byte-identical
  lists on repeat. `FileSort` collapses to two behaviours (newest, most liked);
  `RefreshIndex` pages the Recommend feed back in time deterministically.
* Only two endpoints vary from call to call, and both draw from tiny curated lists:
  `/Cloud/GetHotTag` (tags) and `/Cloud/GetHotExpert` (featured artists). With the
  user's agreement the 30-minute study targeted those two. Full numbers are in
  `report.md` (generated by `analyze.py` from `samples.jsonl`).

## The two random samplers

Study: 1801 requests over 30 minutes, one per second, alternating the two endpoints,
test account `test_01`. No failures, median latency about 80 ms.

| | `/Cloud/GetHotTag` | `/Cloud/GetHotExpert` |
|---|---|---|
| items per call | always 5 | always 10 |
| duplicates within a call | never | never |
| pool size | **24 tags**, all seen by call 14 | **25 artists**, all seen by call 8 |
| distribution over the pool | uniform (chi-square p = 0.74) | uniform (chi-square p = 0.96) |
| pairs drawn independently | yes (p = 0.82) | yes (p = 0.999) |
| order within a call | fixed underlying sequence | fixed underlying sequence |
| memory between calls | none (consecutive overlap = random-pair overlap) | none |
| pool changed during the run | no (first vs second half p = 0.91) | no (p = 0.99) |
| needs a token | yes (`ReturnCode 11` without one) | no |
| reacts to RegionId, Language, StartNum/EndNum, Num, FileSize, Classify | no | no |

Interpretation: each call is a uniform random k-subset of a fixed list, returned in the
list's own order (equivalent to `ORDER BY RAND() LIMIT k` and then re-sorting by the
list's rank, or to a per-row coin flip with a fixed count). Every item lands in every
position with the frequency the fixed order implies, so the first slot is not special:
"PON PON" heads every expert list it appears in only because it is first in the list.

### Tag pool (24)

Eight tags of each `TagType` 0, 1 and 2, in the server's fixed order:
`rabbit`, `music`, `party`, `2021`, `Dog`, `cat`, `Newyear`, `song`, `Skeleton`, `panda`,
`Seagull`, `Eve`, `fruit`, `game`, `weather`, `Wish`, `Holiday`, `Snow`, `Snowman`,
`Gingerbread`, `Santa`, `Reindeer`, `Happy` and one tag with an empty name (type 0).
The list is stale seasonal content (`2021`, `Newyear`, `Santa`) and is neither
alphabetical nor grouped by type. Each tag is drawn with probability 5/24 per call.

### Expert pool (25)

25 user ids (12 "Divoom Master Pixel Artist", 1 "Silver", 12 untitled; 11 from JP,
4 CN, 4 US, 2 DE, 1 each RU, FR, UA, CA; levels 14 to 30), in a fixed order that is
neither by user id nor by level, so presumably a hand-curated rank. Each is drawn with
probability 10/25 per call. The full list with counts is in `report.md`.

## Sensitivity of the method

With pools this small the estimators agree exactly (observed = Chao1 = uniform-model
fit, Good-Turing coverage 1.0). The same scripts would resolve pools up to a few
thousand items at this sample size; the request folder keeps every raw response so
the analysis can be re-run or extended offline.

The one item per endpoint flagged as "last seen early" (`music` at call 880 of 901,
`Nick` at call 890 of 900) is the expected one-in-a-hundred gap for a uniform draw,
not evidence of the pool changing.
